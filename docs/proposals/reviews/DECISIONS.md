# Decisions

Made 2026-09-23, against the reviewed design in `docs/proposals/`. Each references the numbered question it answers from the walkthrough.

1. **Implement now vs. buy-in first — local pieces now, Alloy team only for the in-tree component.** Label alignment, hub split, and the KG pusher don't need anyone else's sign-off. Only the in-tree `discovery.network_topology` Alloy component needs a PR into `grafana/alloy`, and that's already deprioritized behind the `http_sd` precursor.
2. **Order — start with (a) label alignment,** minus `management_ip` (see #3), plus the small `NormaliseName` fix the KG spec found (`internal/discovery/lldp/lldp.go`, `internal/discovery/cdp/cdp.go`). Lowest risk, most cleanly reviewed, useful regardless of what happens to the rest.
3. **`management_ip` — dropped.** Its only real use case was a backup join key for snmp_exporter correlation; `sys_name` already covers that. Not worth the unresolved conflict with the "no raw IP in a label" invariant for an unproven payoff. Revisit only if `sys_name` proves insufficient in practice.
4. **Breaking-change migration — hard cutover, one coordinated major-version bump.** Matches this repo's own existing precedent (issues #20/#27/#31/#98/#100-102, `otlp-schema.md`'s major-bump policy). No dual-emission compatibility window.
5. **Alloy forward-direction discovery→SNMP-targets — dropped.** Keep only the reverse direction (seed topology-exporter's BFS from an existing SNMP target list), which was independently assessed as lower-risk/higher-value. The forward direction had two independent objections (real NOC practice, the flap-to-zero bug) and no reviewer found anything comparably wrong with the reverse direction.
6. **Core/hub split — two binaries** (`cmd/topology-exporter`, `cmd/topology-hub`), as designed. Only option that actually removes the measured 18k `client-go` symbols from the default build.
7. **Federation hub decommissioning — no forced decommission date.** Keep it running indefinitely alongside the KG pusher for anyone who wants it; document that both can coexist. (Overrides the coordinator's original time-boxed suggestion — explicit call from Colin.)
8. **KG-push architecture — build the pusher in topology-exporter now, with a swappable transport interface.** Checked `grafana/alloy` directly: no generic "push arbitrary records to a write API" mechanism exists anywhere (only OTLP-signal-shaped exporters, each locked to one vendor translator). A future generic Alloy component for this wouldn't be smaller than `discovery.network_topology` — likely bigger, no prior art for the inter-component data type, and it'd inherit the same stateful-process/reload mismatch that already ruled out an Alloy-native metrics component. The matching logic (`hub_merge.go`-derived, LLDP/CDP-specific) and the transport (batch/auth/TTL push) are cleanly separable today — drew the boundary at a `Writer.WriteGraphBatches(ctx, []GraphBatch) error` interface (added to `knowledge-graph-boundary-stitching.md` §11), so a future handoff to Alloy or anything else only touches the transport implementation, never the matching code.
9. **Bidirectional traversal — resolved, one direction suffices.** Read `asserts-adi`'s actual read path (`KgReadController.lookupConnectedEntities`, its predecessor, and the search/graph-building service) — all three build Cypher via `relationshipBetween`, Neo4j's Cypher DSL method for an explicitly undirected pattern; core openCypher semantics mean a single directed write is found regardless of which side queries it. The Write API itself has no `bidirectional` field and creates no auto-reverse edge, confirming writes are genuinely single-direction — the design's "push both directions" hedge was unnecessary and has been removed. (One narrow exception exists — `RedisKGraph.getEntityWithUplinks` uses a directed pattern for RCA uplink lookups — but it's hardcoded to a fixed relation list that doesn't include `CONNECTED_TO` and can't be extended by a tenant write, so it doesn't apply here.)
10. **Rate limiting — resolved, hybrid design added to `kg-boundary-pusher-sketch.md`.** Reuses this repo's own `golang.org/x/time/rate` idiom (already the house pattern for the SNMP per-target limiter, same context-seam approach) for a proactive per-second cap on the pusher's batch-POST loop, plus Alloy's exact retry/backoff constants (5s initial, 1.5x multiplier, 0.5 jitter, 30s cap, 5min budget) for reactive handling — applied only to 5xx/network errors, never 4xx, since KG writes are idempotent MERGE upserts and safe to retry (confirmed: `docs/kg-write-api.md` documents no rate limit at all, so this is pure client-side insurance, not compliance with a documented limit).
11. **LD-15/LD-19 doc-accuracy bugs in `docs/architecture.md` — fix now**, standalone, unrelated to everything else.
